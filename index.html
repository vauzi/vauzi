Case study: the month-end payroll incident

A corporate payroll surge made the Q-Cash gateway time out. These four steps restored it in under 15 minutes and protected the 99.9% SLA.

  1. T+00:30

    Detection via Prometheus alert

    A Slack notification flagged the HTTP 504 rate on qlola-qcash-gw crossing the 1.8% threshold during concurrent payroll runs.

  2. T+03:15

    Isolation via ELK traces and pg_stat_activity

    An unindexed transaction status history query ran full sequential scans and exhausted the connection pool.

  3. T+09:40

    Fast remediation

    Non-critical reporting queries were rerouted to a read replica, pool limits adjusted temporarily, and statement timeouts applied so the clearing queue could drain.

  4. T+14:20

    Permanent hardening

    Query refactored with a CTE and a partial index created on (corp_id, status) WHERE status = 'PENDING'. No regressions since.

Before: 2,420 ms (Seq Scan)
SELECT t.*, a.corp_name
FROM transactions t
LEFT JOIN corporate_accounts a
  ON t.corp_id = a.id
WHERE t.corp_id = $1
  AND t.status IN ('PENDING','PROCESSING')
  AND t.created_at >= NOW() - INTERVAL '30 days'
ORDER BY t.created_at DESC;

-- Seq Scan, rows removed: 1,842,910
-- Execution Time: 2420.14 ms
After: 42 ms (Index Scan)
WITH active_tx AS MATERIALIZED (
  SELECT id, corp_id, status,
         created_at, amount
  FROM transactions
  WHERE corp_id = $1
    AND status IN ('PENDING','PROCESSING')
  ORDER BY created_at DESC
  LIMIT 50
)
SELECT atx.*, a.corp_name
FROM active_tx atx
JOIN corporate_accounts a ON atx.corp_id = a.id;

-- idx_tx_active_corp, Execution: 41.82 ms
Before2,420 ms
After42 ms
